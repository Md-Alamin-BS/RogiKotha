## Forbidden

<!-- Populated by practices-discovery affirmation gate. -->
<!-- Format: NEVER [behavior] (affirmed [date]) -->
<!-- Example: NEVER throw exceptions across service layer boundaries (affirmed 2026-05-17) -->

- NEVER put tool, model or agent identity into any commit (author, committer, message or trailer), pull request, document, code comment, generated file or AI-DLC record: no `Co-Authored-By` trailer, no "Generated by/with" footer, no badge or watermark; commits carry only the human's own git identity, and existing records stay as history, never rewritten (AGENTS.md, D8). (affirmed 2026-10-15)

- NEVER use real personal data: every person, doctor, facility and account in code, seed, fixtures and tests is synthetic, and no real person or facility is named in a negative account (PRODUCT.md, `01-conventions.md` §14). (affirmed 2026-10-15)

- NEVER hard-code a user-facing string in components or server code; all copy, error messages (as `messageKey`) and emails go through `packages/i18n` keys in both languages (`01-conventions.md` §6). (affirmed 2026-10-15)

- NEVER let a number stand for quality: no star rating, no combined score and no rating column anywhere in code or schema (PRODUCT.md hard rule). (affirmed 2026-10-15)

- NEVER render a missing value as `0` (PRODUCT.md hard rule). (affirmed 2026-10-15)

- NEVER describe evidence as "verified" or "approved" (PRODUCT.md hard rule). (affirmed 2026-10-15)

- NEVER let facility feedback enter a doctor's summaries or aggregates; this is enforced in the data layer and tested at query level, not only in copy (PRODUCT.md hard rule). (affirmed 2026-10-15)

- NEVER show a reporter's identity to the reported person or in any public projection; in the staff console it reads "restricted", never blank (PRODUCT.md hard rule). (affirmed 2026-10-15)

- NEVER offer a "highest rated" sort (PRODUCT.md hard rule). (affirmed 2026-10-15)

- NEVER build two Units in parallel when they depend on each other or touch the same files, and NEVER let a parallel build put tool, model or agent identity into a commit; independent Units are built in parallel through AI-DLC's swarm with one worktree and test database each (D13 as changed by the owner, FD-094). (amended by the owner 2026-10-29)

- NEVER run `git reset --hard`, `git checkout --` or `git clean` on a dirty working tree (`01-conventions.md` §12). (affirmed 2026-10-15)

## Mandated

<!-- Populated by practices-discovery affirmation gate. -->
<!-- Format: ALWAYS [behavior] (affirmed [date]) -->
<!-- Example: ALWAYS use Result<T,E> for fallible operations in service layer (affirmed 2026-05-17) -->

- ALWAYS give every user-facing string a Bengali and an English entry with the same key, adding both `packages/i18n/messages/en.json` and `bn.json` in the same commit; a key without its Bengali string is a build failure, never a TODO (ADR 0011, FD-024, AD-9). (affirmed 2026-10-15)

- ALWAYS check the dependency-check log before a first-time integration, a new dependency or a big feature: reuse an entry under 3 days old, otherwise verify the current stable release (not just the newest), skim its changelog and known issues, and append a dated entry to `docs/status/dependency-check-log.md` before implementing (AGENTS.md). (affirmed 2026-10-15)

- ALWAYS research before starting new work or changing existing behaviour: check that the approach fits this codebase's architecture and conventions, the product need in `docs/`, and current best practice; propose a better option openly instead of silently deviating or silently doing worse, and save non-trivial findings under `docs/planning/research/` (AGENTS.md). (affirmed 2026-10-15)

- ALWAYS treat the decisions in `docs/status/decision-log.md` (FD-001 onward) as binding; a change to a hard rule, a data boundary or a founder decision needs a new FD entry in the decision log before any code changes (master plan §10). (affirmed 2026-10-15)

- ALWAYS show distributions with exact counts and their denominators (PRODUCT.md hard rule). (affirmed 2026-10-15)

- ALWAYS render a missing value as "Not provided" or "No documents" (PRODUCT.md hard rule). (affirmed 2026-10-15)

- ALWAYS show "Limited data" when the number of eligible accounts is below the configured threshold; the threshold is a deferred product decision and the demo uses a placeholder value (PRODUCT.md hard rule). (affirmed 2026-10-15)

- ALWAYS show "Registration not verified" on every doctor until BMDC verification exists (PRODUCT.md hard rule). (affirmed 2026-10-15)

- ALWAYS word evidence as "Documents attached — not medically validated" (PRODUCT.md hard rule). (affirmed 2026-10-15)

- ALWAYS render a reviewer's claim as "Reviewer's label", framed as the author's claim and never as a platform finding (PRODUCT.md hard rule). (affirmed 2026-10-15)

- ALWAYS treat access to original evidence as a separate, audited permission, and fail closed when scanning cannot run, so the item never advances (PRODUCT.md hard rule, FD-035). (affirmed 2026-10-15)

- ALWAYS keep the persistent medical-advice disclaimer and the non-blocking emergency guidance (999, 16263, crisis line, last verified) where the prototype has them (PRODUCT.md hard rule). (affirmed 2026-10-15)

- ALWAYS order lists neutrally, by relevance, most accounts or most recent (PRODUCT.md hard rule). (affirmed 2026-10-15)

- ALWAYS give Bengali and English equal product status, with numerals that follow the active language and no capital-letter transform in Bengali (PRODUCT.md hard rule, FD-024). (affirmed 2026-10-15)

- ALWAYS keep the synthetic-data demo marker visible ("Demo — fictional records"), and never present synthetic content as real (master plan §1, AD-14). (affirmed 2026-10-15)

- ALWAYS run every Unit through all validation steps before merge: `pnpm check` and the whole cumulative `pnpm smoke` green, every acceptance row executed and recorded as expected against observed, the reviewer's diff review passed, and for high-risk Units 3–5 adversarial tests by a separate agent plus the owner's written sign-off (owner, 2026-10-15). (affirmed 2026-10-15)

- ALWAYS record every defect, workaround or assumption as an `ISS-` row in `docs/implementation/ISSUES.md` with an S1–S4 severity and the Unit/Bolt id it was found in, and list those `ISS-` ids in that Unit's Build and Test record (owner, 2026-10-15). (affirmed 2026-10-15)

- ALWAYS ask the owner about any open point instead of deciding it, explaining each option and giving a suggestion (owner, 2026-10-15). (affirmed 2026-10-15)
