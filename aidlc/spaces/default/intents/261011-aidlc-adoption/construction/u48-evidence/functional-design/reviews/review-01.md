Advisory pass. I did not count the known limits mismatch (10 MB / 5 / 50 MB against C18 and AC7.1.3's 15 MB / 10 / 100 MB). What I checked and found sound: the authorization chain (`reviewIdForPublicId`, then `isReviewAuthor` and `isReviewPublished`, all inside the intake transaction, with one `404` for every foreign case); the 32-hex key with path containment (BR3.1, BR3.2); no streaming read for the web tier in the rules and the database CHECK keeping originals non-public (BR3.5); the three-field `evidence.stateChanged` payload with no `uploaderAccountId` (BR4.7); the exact wording rule (BR5.3, BR5.4); and the scanner-unavailable path never moving an item forward (BR4.5). `preview_ready` in `PUBLIC_EVIDENCE_STATES` is safe to count in release 1. The design only reaches it after the worker re-validates the bytes and clamd answers exactly `OK`. Only the count is public. Seeded `failed` rows are not counted. Nothing has a page cache that could keep a stale count: no `'use cache'`, `unstable_cache` or `revalidate` appears in `apps/web/src`.

### Summary

The security core holds: authorization, path containment, originals never served, fail-closed scanning, the outbox payload without `uploaderAccountId`, and a safe `preview_ready` count. Four design gaps block a clean implementation: how the job knows it is on its last attempt and its queue options, no terminal state for crashed or expired attempts, a props change that breaks C16 and U47's mount, and a structure check that lets truncated and polyglot files through, so test A1 would fail. Each needs only a small, local revision.
