## Better Auth 1.7.x — the four tables checked against the library, not the hand-off

Task step 5 told the implementer to verify the four tables against Better Auth's own docs and to
write out the exact `modelName`/`fields` mapping T-101 must pass the adapter. Both halves were
re-checked here against Better Auth's **tagged v1.7.4 source** (`packages/core/src/db/get-tables.ts`,
`packages/drizzle-adapter/src/drizzle-adapter.ts`, `packages/core/src/db/schema-diff.ts`, and the
CLI's own generated-schema snapshot), diffed back to v1.6.31, because the master plan §3 pins
Better Auth **1.7.3**.

**The column set is exactly right.** All four tables carry every column Better Auth 1.7.3 declares
and no extra one. Three points worth recording:

- `account.issuer` is **correctly absent**. It was `required: true` in 1.7.0–1.7.2 only and was
  removed in 1.7.3; on 1.7.3+ a leftover NOT NULL `issuer` is now an *error*, because 1.7's new
  runtime schema check rejects any extra NOT NULL column without a default that Better Auth never
  writes. The schema adds no such column anywhere — so the check will pass.
- `auth_users.name` is nullable where Better Auth declares it `required: true`. Harmless: the 1.7
  check only reports `missing-table`, `missing-column` and `unexpected-required-column`, never the
  reverse, and Better Auth always supplies a value. Data model §1 says `name` is unused anyway.
  Recorded as `ISS-113` so T-101 does not re-derive it.
- The three indexes Better Auth's own generator emits (`session_userId_idx`, `account_userId_idx`,
  `verification_identifier_idx`) are missing — `pg_indexes` on `auth_%` returns only the four
  primary keys plus `auth_users_email_unique` and `auth_sessions_token_unique`. Also `ISS-113`.

**The mapping comment is wrong, and it is annotated as verified.** `schema/auth.ts:35-38` says
"Verified against Better Auth's 1.7.x Drizzle-adapter docs". It is not:

- `modelName: 'auth_users'` resolves against `schema[modelName]` — the **JavaScript export key** of
  the Drizzle schema object, not the SQL table name. This package exports `authUsers`, so the
  adapter would throw `The model "auth_users" was not found in the schema object`.
- `fields: { emailVerified: 'email_verified', … }` resolves against the **Drizzle property key**,
  not the SQL column name (`schemaModel[getFieldName(...)]`). The tables use the idiomatic
  `emailVerified: boolean('email_verified')`, so the adapter would look for a property literally
  named `email_verified` and fail. The correct answer is **no `fields` block at all** — camelCase
  key + snake_case column name is exactly what `npx auth generate` emits.
- Neither `usePlural` (it appends a literal `"s"` → `auth_userss`) nor a global casing option is a
  fix; `casing: 'snake'|'camel'` belongs to the built-in Kysely config, and the adapter's
  `camelCase` flag only affects CLI generation.

Logged as **`ISS-112`** (S2, owner T-101). This is the finding with the longest fuse in the review:
the tables are right, so nothing fails today, but T-101 is an M3 task already flagged as the
riskiest in the plan, and it would start from an instruction that is confidently wrong.
