## Mechanical verification of the strip

Because this change is 99 near-identical edits, it was checked by construction rather than by
reading all of them:

- The `packages/contracts/` half of the diff is **198 changed lines** (99 removed, 99 added) and
  **every single one** is an `import`/`export … from` statement — filtering the diff for any line that
  is not one returns nothing. No logic, type, export or comment line changed anywhere in the package.
- Stripping `.js` from each side and sorting leaves every line paired an even number of times, i.e.
  each removed specifier has an added twin differing **only** by the suffix. No specifier was
  retargeted while it was being edited.
- `packages/contracts/src` now holds **99 relative specifiers and 0** `.js`-suffixed ones.
- `packages/contracts/package.json` exports `./src/index.ts` directly (source-only, no `dist`), and
  `tsconfig.base.json` sets `moduleResolution: "bundler"` — the mode that *expects* extensionless
  relative specifiers. Nothing in the repo consumes this package through Node's own ESM resolver, so
  removing the suffixes cannot break a runtime path: `packages/database` and `packages/test-support`
  reach it through `tsx`, everything else through Vite or Turbopack.

The one non-mechanical part of the diff is `emergency/page.parity.test.ts`, whose job legitimately
changed: it used to guard a hand-typed local copy against the real default, and there is no longer a
second copy to drift. It was **repurposed, not deleted** — it now pins `DEFAULT_CONFIG_VALUES.emergency`
to the four exact values the storyboard and `Emergency.test.tsx` expect, so a silent change to the
shared default still fails a test. That is the right call: the weaker alternative would have been to
drop the file.

## Verdict

**PASS** — merged.

`ISS-183` is a genuine `S2`, but it is a finding in **already-merged T-004/T-005 code that CR-005 does
not own** and is not a regression this branch introduced; per `04-handoff-and-validation.md` §4.1 it

## Residual risk / decisions for the human

- **`CR-009` needs queueing, not a decision.** It is the other half of the bug CR-005 fixed, it is
  fully specified, and it will block the first Phase-2 page that reads the database from a server
  component. Queuing it before or alongside T-201 is cheaper than discovering it mid-task, which is
  exactly how `ISS-133` was found in the first place (T-207a, mid-task).
- **Worth noticing as a pattern:** both halves of this bug were invisible until a *consumer* appeared.
  Neither `pnpm check` nor any test catches an unused-yet package's resolution mode, because nothing
  in `apps/web` imported those packages. A cheap permanent guard would be a tiny `apps/web` route (or
  a build-time import) that pulls each workspace package's barrel, so `next build` proves resolution
  for all of them on every run.
