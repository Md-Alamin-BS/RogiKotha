## Settled in this design without a question

These follow from the FD entries, the project rules or the code, so they are design decisions, not open points. Each is explained in `functional-spec.md` § 9–§ 10.

- **The corpus is regenerated by the port, never edited by hand.** Every corpus file except `types.ts` and `index.ts` carries "Generated … Do not hand-edit". The new records reach the seed by running `pnpm --filter @rogikotha/test-support port` against the expanded prototype (owned paths: Question 4).
- **The port must keep existing derived values.** A plain re-run would change the avatar hue of five existing personas (`nadia_k` 50 → 198, `rumana_h` 87 → 235, `Dr. Farhana Rahman` 124 → 60, `health_tips_bd` 161 → 97, `shafiq_ctg` 198 → 134), because hues are handed out in discovery order and new review authors are now discovered first. The port pins the hue of every persona that existed before FD-089 and continues the same sequence for new ones (BR2.4).
- **Follow-ups follow the prototype's own reading rule.** The prototype's `followUpsFor` returns a review's chain or, when it has none, its single inline `followUp`; r17 and r24 have only the inline one. The port reads follow-ups the same way, so 21 follow-ups are ported, not 19 (BR2.2).
- **An anonymous comment in an anonymous review's thread reuses that thread's persona.** k31 sits in r15's thread, and r15 is anonymous; the port today would emit a second `anon:r15` persona and a duplicate account, which breaks the corpus invariant test. It emits one persona, as T-401 step 4 describes for the review's anonymous author (BR2.3).
- **Two new Banglish aliases are classified as Banglish.** `shash` (c9) and `mathabatha` (c10) are Latin-script Bengali; the port's hard-coded list (`dayabetis`, `chulkani`) gains both (BR2.5).
- **Doctor chambers link to the new branches.** New chambers are named "<organisation> — <branch>" (for example "Kashful Community Hospital — Shaheb Bazar branch"), which the seed's name match does not recognise. The seed also matches that composite form; no existing chamber link changes, because no existing chamber name has that form (BR3.2).
- **The seed parses "N months ago".** n9 and n10 say "2 months ago" and "3 months ago"; the current parser throws on them. A month is read as 30 days (`ASSUMPTION(CR-012)`, BR3.3).
- **MOD-2018 is seeded as a real appeal.** It appeals the hiding of comment k27; the seed's appeal branch today handles review targets only and would leave an `appealed` case with no decision and no appeal. Comment targets get the same treatment as MOD-2011: the comment is hidden, one `hide` decision, one open appeal by the comment's author (`shafiq_ctg`) with the prototype's appeal text. MOD-2011's rows stay exactly as they are (BR3.4).
- **MOD-2033's padding is explicit and limited to MOD-2033.** A per-case padding table holds one entry, MOD-2033 → `factual` (FD-039); a case whose report count exceeds its listed reasons without an entry fails the seed instead of inventing reasons. No other case is short today (BR4.1, BR4.2).
- **No i18n key is added.** Every new record maps to an existing key, enum value or stored text (`functional-spec.md` § 10.6), so `packages/i18n/messages/{en,bn}.json` and i18n parity stay unchanged.
- **A doctor's and a branch's missing fields come from the schema, not from invented gaps.** The prototype fills every field it has on the new doctors and facilities; the gaps that make "Not provided" demonstrable on them are `doctors.about_*` and `facility_branches.address_*`, which the prototype never provides (BR1.6; Question 11).
- **No new dependency.** The Unit adds no library and changes no version, so no dependency-check entry is needed.
