## What exists now

The outbox relay is transactional (FD-038). One relay tick is one transaction on one
connection, built by `PgOutboxRelayStore` (`packages/database/src/queue/outbox-relay-store.ts`):

- `BEGIN`, `SET LOCAL statement_timeout = '5s'`, `SET LOCAL idle_in_transaction_session_timeout = '10s'`
  (`ISS-249`);
- claim up to 50 unprocessed events, oldest first, `FOR UPDATE SKIP LOCKED`, without marking
  them (`PgOutbox.claimUnprocessed`);
- for each event, a savepoint; the worker's plan names its jobs; each job is sent with pg-boss
  `send(..., { db })` on the same connection; then the event is marked processed and the
  savepoint released;
- a failed job rolls back to the savepoint (so the event keeps no job), adds one attempt, and
  after the fifth attempt marks the event processed with no job (`dead`);
- `COMMIT`; the outcomes are returned only after it, and the worker logs them then.

A failure outside an event's savepoint (a connection or commit error, a planning error, a
missing queue) rolls the whole batch back and rejects; the poller logs `job.failed` for
`outbox.relay` as before.

Queues are created from one declaration, `packages/database/src/queue/queue-declaration.ts`:
every C15 job is listed, every entry is `exclusive`, any other name falls back to `exclusive`,
retries are 5 with backoff (3 for `evidence.process`, FD-076), `expireInSeconds` 300
(`ISS-251`). `PgBossQueue.ensureQueue` creates the queue from it, reads it back and throws
`QueuePolicyMismatchError` (queue, both policies, `pnpm db:reset`) when a stored queue has another
policy. `PgBossQueue.enqueue` now returns `EnqueueResult`: `enqueued`, `deduplicated` (a `null`
from pg-boss confirmed by an in-flight job with that key on the same executor), or the failure
`job_not_enqueued` (an unconfirmed `null`; the queue loses its ensured mark). A send that pg-boss
rejects with `Queue <name> does not exist` clears the ensured mark and rejects with
`QueueMissingError`, which the relay treats as a batch fault (design review R-01). With an
`executor` (the caller's transaction) `enqueue` does not create the queue; the caller ensures it
before opening the transaction.

The worker (`apps/worker/src/handlers/outbox-relay.ts`) keeps the routes (`RELAY`, unchanged)
and now owns the pure parts: `planEvent` (key `<job>:<eventId>`, data
`{ eventId, name, payload }`), `decideFailure`, `logOutcomes` (`outbox.unmapped`,
`outbox.relay_failed`, `outbox.dead`, `outbox.job_deduplicated`, with event name, event id,
job, attempts and error code only). `relayOnce` ensures every routed queue, relays one batch
and logs its outcomes. `main.ts` ensures every routed queue before the first tick and exits 1
with a `worker.start_failed` line when one fails (`queue_policy_mismatch` or
`queue_ensure_failed`).

`runReset` drops `pgboss` and `public` in one transaction (`DROP SCHEMA IF EXISTS … CASCADE`
each), under CR-007's `lock_timeout` 10 s and `statement_timeout` 60 s; a blocked drop names
every backend holding a lock on either schema or a relation in it, looked up by schema name.
The message is now `db:reset could not lock schemas pgboss and public within lock_timeout 10s;
blocked by backend pid N (role R, …)`. The migrate step reinstalls `pgboss` as `rk_app` and
re-runs `0006_pgboss_grants.sql`. The once-per-run reset, the guarded sweep and the
`APP_MODE=production` refusal are unchanged.

Both env loaders call `config({ path, quiet: true })`.

## Rules later Units must know (`ISS-253`)

- Every queue is `exclusive`: at most one queued, retrying or active job per key, and a send
  without a key counts as the empty key.
- U8: every `mail.send` needs its own key (for example `mail.send:<deliveryId>`); `queueEmail`
  on the command's transaction passes `executor` and calls `ensureQueue` before the transaction.
- U18: if `search.refresh` keys by document to coalesce, its declaration entry becomes `stately`.
- U29: `retention.expire`'s cron sends carry no key, so an occurrence while the previous run is
  in flight is dropped; check that this is wanted.
- U32: `moderation.openRepetitionCase` keys by `repetition:<reviewId>` through its own route rule.
- Every handler stays idempotent: a job with the same key can run again after the first finished.

## Fragile or surprising

- pg-boss answers a send to a queue whose row is gone in two ways, depending on its 60 s queue
  cache: `null` while the queue is still cached (an attempt is counted, the queue is re-ensured
  next tick) and a thrown `Queue … does not exist` afterwards (the batch rolls back, no attempt).
  Tests T8, T9 and T4 build the first case, T17 the second.
- pg-boss 12.37+ moves that failure to the `COMMIT` (`23503`); a pin upgrade must handle it
  (`ISS-257`).
- The ISS-202 probe and T15 reset the test database mid-run, as before; files still run one at
  a time.
