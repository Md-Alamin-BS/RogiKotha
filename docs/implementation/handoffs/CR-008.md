## Fragile or surprising

- **sharp 0.35.4's `withExif` silently drops unrecognised top-level keys.** `GPS` looked like a
  reasonable key (the EXIF spec calls it the GPS IFD) and produced no error — it just never wrote
  anything. Sharp's own docs example for GPS data uses `IFD3`, which is the only key that actually
  works; confirmed empirically before trusting the docs (wrote a throwaway script, parsed the
  output's EXIF by hand). The lesson generalises: `withExif`/`withMetadata({ exif })` apparently
  accepts *any* object shape without validating it against what libvips will actually honour, so
  any future EXIF-writing code in this package should keep the same "re-read and assert" pattern
  this fix added rather than trusting the call succeeded.
- **`pnpm db:reset` does not touch `STORAGE_ROOT`.** Verifying the "Derivatives on disk" acceptance
  row first showed **12** item directories, not 6 — this worktree already had 6 from an earlier
  provisioning seed run, and a bare `db:reset && db:seed` mints fresh random evidence-item
  `publicId`s without ever cleaning up the old directories. Not a CR-008 defect (confirmed by
  deleting `.data/storage` and re-running from clean, which gave exactly 6) but worth knowing before
  trusting a directory count in a worktree that has been seeded more than once (`ISS-192`).
- **`seed-notifications.ts` had to run last, not merely "after content" as the task text's minimum
  says.** Two of the five notifications' `params` need an evidence item's public id (seeded by
  `seed-evidence`) and a moderation case code (seeded by `seed-moderation`), both later than
  `seed-content` in the existing step order — so this step is registered after all six other steps,
  not spliced in earlier.
