## What exists now

- **Better Auth behind a port** (FD-093, Q12): `better-auth@1.7.14` lives only in `apps/web/src/server/better-auth/` (instance, gateway, library-call scope, session cookies). The application reaches it through the `AuthGateway` port. The library's hooks and callbacks act only inside a gateway scope, so a direct `auth.api.signUpEmail` creates no user (BR1.7, BR7.9).
- **Commands** in `packages/application/src/modules/account/`: `register`, `verifyEmail`, `resendVerification`, `resendOwnVerification`, `signIn`, `signOut`, `signOutEverywhere`, `requestPasswordReset`, `resetPassword`, `changePassword`, `updatePreferences`, `submitFeedback`, and the queries `listSessions` and `getOwnAccount` (the masked own address, FD-096). Each is built with `defineCommand` or `defineQuery` (`command.ts`: parse, the `requires` order, `onRefused`, `recorded`, one transaction).
- **Sign-in protection**: 30 failures per 15 minutes per network and 10 per email, the FD-063 delay (1, 2, 4, 8, 16, 30 s) as a refusal, the severe-activity email and `account.securityEvent` after the response, one password verify on every failure path (a dummy hash for unknown and deleted addresses).
- **Sessions**: absolute 30 days from creation, no IP stored, HttpOnly and SameSite=Lax cookies. `getActor()` (`apps/web/src/server/auth.ts`, on `resolveActor`) reads the status on every request: suspended, banned and deleted accounts are anonymous with a `refusal`; the Actor never carries a staff role or a capability (BR4.3).
- **Email**: `queueEmail` writes the `email_deliveries` row and the `mail.send` job on the command's own transaction (`PgJobQueue`), keyed per delivery. The recipient is encrypted with the mail-only `MAIL_RECIPIENT_KEY` (FD-095). The worker's `mail.send` decrypts with that key only, renders from the i18n message files (FD-098) and sends through Mailpit.
- **Adapters**: Argon2id hasher, AES-256-GCM `Crypto` with per-purpose HMACs, the memory rate limiter and the SMTP transport, in `packages/adapters`.
- **Database**: migration `0009_auth_indexes_and_email_dedupe.sql` (the three auth indexes and `email_deliveries.dedupe_key`), `PgUnitOfWork`, `PgAccountRepository`, `PgEmailDeliveryRepository`, the recursive audit check (ISS-108).
- **The `/api/auth/[...all]` route** forwards only `/api/auth/ok`; every other path answers 404 with a JSON `null` (BR7.1 as narrowed in Step 15).
- **Demo slice**: its register, sign-in and sign-out forms and its session read now run through these commands (ISS-391). Every demo page and flow still works. Register no longer signs in: a new and an existing address both go to the sign-in page (ISS-427).

## Spike results (Step 4, `better-auth@1.7.14`, memory adapter)

- The reset token is a `verification` row: `identifier = 'reset-password:<token>'`, `value` = the auth user id, 24 characters. So the reset command reads the token's account without consuming it (review point 1, mechanism (a)).
- The email-verification token is a signed JWT (24 h) and writes no row.
- An `AsyncLocalStorage` scope opened around `auth.api.*` is visible in `databaseHooks` and in both email callbacks; `user.create.before` returning `false` makes `signUpEmail` fail with no row.
- `signInEmail` with `returnHeaders: true` returns the `set-cookie` values; `advanced.ipAddress.disableIpTracking: true` leaves `ip_address` as `''`.
- With the auto sign-in refused, `verifyEmail` sets `emailVerified` first and then fails "Failed to create session"; the gateway reads that, inside the verify scope, as "verified, no session" (BR2.2).
- Found later (Step 10): with `autoSignIn: false`, `signUpEmail` answers an existing address with a fake user instead of an error; the gateway checks the address itself (ISS-417).
