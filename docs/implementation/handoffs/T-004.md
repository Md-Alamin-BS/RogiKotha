## How I verified it

`pnpm --filter @rogikotha/database typecheck`, `eslint packages/database`, `pnpm i18n:check`,
`pnpm -r build` — all green. `pnpm test`/`pnpm test:int` are **red** in this environment only
because a native Windows PostgreSQL 18 service occupies host port 5432 ahead of the Docker
`rogikotha-postgres-1` container (`ISS-084`, full detail in the task file's own hand-off and
`ISSUES.md`) — no Node process on this machine can reach the container. Worked around for
verification: piped `0000_init.sql` then `0001_grants_part1.sql` through
`docker exec rogikotha-postgres-1 psql` into a throwaway scratch database. Confirmed live: 30
tables, all 36 enum types with correct labels, `rk_worker` denied on `persona_links`/`auth_users`,
allowed `SELECT` on `personas`, allowed `INSERT` but not `SELECT` on `audit_events`, and a table
created afterward by `rk_app` correctly inherited the worker's default-privilege grant. Scratch
database dropped afterward — nothing left behind in the shared container.

No smoke assertion was added: this task's "Tests to write" are the `*.int.test.ts` files themselves
(`migrations.int.test.ts`, `client.int.test.ts`).

**Update (follow-up session, same day):** `ISS-084` is resolved (founder chose to remap the compose
port to `5433` rather than touch the native service). Unblocking it surfaced two more real bugs in
this task's own code, now fixed: `ISS-092` (S1 — `db:reset` could silently leave `public` empty on a

`pnpm smoke` is green (3 files/5 tests). The scratch-database verification described above turned out
to be accurate — nothing it found needed correcting once the real suite could run.

## Fragile or surprising

- **`ISS-084` (S1, blocking):** the port-5432 conflict above will hit every future session that
  touches `packages/database` on this machine (T-005, T-007, T-009, …) until a human frees the port.
  Check `Get-NetTCPConnection -LocalPort 5432` first if `pnpm test:int` fails with a password error
  that looks wrong — it is almost certainly this, not a credentials bug.
- drizzle-kit 0.31.10 cannot serialize a JS `BigInt` column default (`TypeError: Do not know how to
  serialize a BigInt` from its snapshot differ) — `schema/demo.ts`'s `offset_seconds` uses a
  SQL-literal `sql\`0\`` default instead of `0n` (`ISS-087`). If you add another `bigint` column
  with a default, use the same pattern.
- The int test suite runs both `*.int.test.ts` files sequentially against one `DATABASE_URL_TEST`
  database (`vitest.config.ts` sets `fileParallelism: false`); `test-setup.ts` resets it once via a
  cached promise. Adding a third int test file needs no config change, just don't rely on ordering
  between files for state.
- `repositories/{directory,taxonomy,config,audit}.ts`'s method names are this implementer's reading
  of the command catalogue, not literal task text (`ISS-091`) — the owning tasks (T-201, T-204,
  T-404, T-407, T-408) can rename freely when they add the `implements <Port>` clause.
