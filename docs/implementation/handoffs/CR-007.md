## What exists now

The `database` project resets `rogikotha_test` once per Vitest run, in a `globalSetup`
(`packages/database/src/global-setup.ts`), before any test file starts. Test files only open
their pool (`test-setup.ts`). Before the change every collected file ran its own drop and
migrate cycle: 10 per `pnpm test:int`, plus the ISS-202 probe's deliberate mid-run reset,
which is unchanged.

`runReset` in `reset.ts` no longer waits forever on a lock:

- every session opened from the reset URL gets `lock_timeout = 10s`, passed as the connection
  string's `options` (`-c lock_timeout=10s`), so the drop, the schema and extension statements,
  the migrations and the pg-boss install all get it;
- the drop runs in its own transaction with `SET LOCAL statement_timeout = '60s'`;
- when the drop times out it rolls back, reads `pg_locks` for granted locks on schema `public`
  and the relations in it, and throws
  `db:reset could not lock schema public within lock_timeout 10s; blocked by backend pid N (role R, application "A", state S)`;
- the drop is `DROP SCHEMA IF EXISTS public CASCADE` (`ISS-244`).

`terminateStaleTestBackends(url)` is new in `reset.ts`. It returns
`{ ok: false, reason }` without opening a connection unless the URL's database name ends in
`_test` or `_test_b`. Its SQL repeats the check (`current_database() ~ '_test(_b)?$'`), so it
matches no row on any other database. It ends only client backends of roles the connecting
role may signal (`pg_has_role(usesysid, 'MEMBER')`), waiting up to 5 s for each to exit. Only
the global setup asks for it (`runReset(url, { terminateStaleBackends: true })`); it prints
one `console.warn` line per run that ended anything. `pnpm db:reset` and `pnpm demo:reset`
never sweep, and `migrate`, `reset` and `seed` still refuse `APP_MODE=production`.

`fileParallelism: false` stays. Per-file isolation is still needed: every file shares one
database, and the ISS-202 probe and the new contention test reset or lock it while they run.

## The `beforeAll` timeout question

The hook timeout fires (the first file's three tests were reported skipped `↓`), but Vitest
cannot cancel the pg query behind it. The `DROP` stays queued in PostgreSQL, and a run killed
from outside leaves it there, where it runs later (`ISS-244`). The driver-level `lock_timeout`
is the real safeguard; the test-level timeout only lets Vitest move on.

## Fragile or surprising

- `pnpm test:int` now takes about 30 s instead of about 22 s, because the contention test
  waits out the 10 s lock timeout on purpose.
- When the global setup throws, Vitest prints `No test files found, exiting with code 0`
  before the real error, although it exits 1 (`ISS-246`).
- Two `pnpm test:int` runs against the same test database at the same time are still not
  safe: the second run's sweep ends the first run's `rk_app` connections. This was already
  the case before (`Parallel-safe with` in the task file).
